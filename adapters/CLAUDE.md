# adapters — bidirectional format conversion and Port implementations

Controller / Presenter / Gateway / DTO all live in this layer. No business-rule decisions, no use-case orchestration.

## File map

| Directory | Contents |

## Rules of this layer

### Stitching intent and runtime state

- `load_apps_file` / `load_service_file` / `SpecSource::resolve_service` are all **async**: they run in the daemon's single-task actor loop (`Daemon::start` once per service, `YamlDumpStore::load` once per record); synchronous `std::fs` would freeze the entire event loop on slow disks/NFS. Likewise `materialise_workspace` uses `tokio::fs::canonicalize` and dedupes already-resolved paths (cwd appears in both `spec.cwd` and `derived_roots[0]`)
- `cfg_dir/<name>.yaml` stores **intent** (zero absolute paths, `${HOME}` placeholders, `script` stores a bare name, `cwd` derived by the daemon), `dump.yaml` stores only `services[].runtime`; `SpecSource` stitches the two together at daemon startup; a missing/corrupt service file MUST NOT keep the whole daemon from starting — `rejoin` logs `warn` then converts that entry into `DumpContents.stranded` (`StrandedProcess { name, pid, token }`) for `resurrect` to sweep; MUST NOT just `return None` (see root `CLAUDE.md` "Environment variables and credentials")
- `<name>.env` is only read by `load_env_file`, never written by pm3: parsing is the pure function `parse_env_file(path, home, text)` (split at the first `=`, `#` comments, strip one layer of paired quotes, duplicate keys error, expand `$HOME` in double-quoted and bare values). Error text carries only path/line/key, MUST NOT carry values. `HOME` is filled in by `with_host_home` from the injected `SpecSource.host_home`; declared values win
- `$HOME` expansion MUST hold three boundaries: `$HOMEBREW_PREFIX` must not be eaten (`continues_a_name` checks the word end), single-quoted values never expand (an escape hatch for passwords that literally contain `$HOME`), no expansion when `host_home` is `None`
- After reading, the loader's `chmod 0600` MUST first exclude symlinks via `symlink_metadata` (failure only warns): `set_permissions` follows symlinks; linking `<name>.env` to a shared credential like `/etc/creds/x.env` would chmod **someone else's** file (symptom: another consumer suddenly gets EACCES while pm3's side shows only one debug log line)
- The two rejection points for `env:` appearing in yaml: `check_declared_names` (apps files go through `split_apps_file`, no resolve, so it must be caught at parse time) and `resolve_entry` (service files + fallback), sharing `reject_env`, reporting `AppsFileError::EnvInYaml`
- `SpecSource::resolve_service` parses the **single-service format** with the dedicated `parse_service_file` (top-level `name:`/`script:`/… directly, no `apps:` array wrapper) and checks `name` against the filename; the `apps:` array appears only in user-written apps files (`pm3 start apps.yaml`)

### Children do not die with the parent

Three platform settings must all hold; missing any one kills services along with a daemon handover: launchd `AbandonProcessGroup`, systemd `KillMode=process`, and bwrap **without** `--die-with-parent`.

### Sandbox and paths

- macOS `sandbox-exec`'s `subpath` only matches real paths; symlinks like `/var/...` don't match → `cwd` and `writable_roots` must be canonicalized before spawn
- Backend program names come from `SandboxProgramSet` (`SandboxBackend::resolve(&programs, search_path)`); `SandboxBackend` itself is just the two labels `Seatbelt`/`Bwrap` and no longer holds path constants; `detect_host_backend` is fed on the `frameworks` side by `SandboxProgramSet::from_config(&config.sandbox)`
- `materialise_workspace` MUST NOT rewrite `spec.sandbox.writable_roots` (fingerprint discipline in root "Identity fingerprint and takeover"): canonicalized results are **appended** to `derived_roots`; not appended again when identical to the declared value
- Expanding `${PM3_SERVICE_CWD}` in `materialise_workspace` MUST come **after** `spec.cwd = real_path(...)`; substituting earlier writes the un-canonicalized cwd into args, exactly reproducing the pitfall above
  Regression tests: `src/tests/workspace_tests.rs::a_placeholder_expands_to_the_real_path_not_the_symlink` and `frameworks/tests/sandbox_isolation.rs::a_confined_app_can_write_through_the_cwd_placeholder`

#### seatbelt (macOS)

The semantics of the four path classes and the "hidden nesting direction" security constraint are in root `CLAUDE.md` "Sandbox"; only SBPL authoring is recorded here.

- Paths always go through `-D KEY=value` parameters + `(param "KEY")`; no user path ever appears in the profile text: this eliminates the SBPL injection surface
- **Only real paths match**: `/etc` and `/var/run` are symlinks (→ `/private/etc`, `/private/var/run`); `subpath`/`literal` written as `/etc/...` or `/var/run/...` never match ⇒ paths MUST be written in `/private/...` form (both mDNSResponder and resolv.conf fell into this)
- **Every `subpath` grant MUST be paired with one `(allow file-read-metadata (path-ancestors (param ...)))`** (write the two lines together in `rules()`): opening a file inside a granted root by **absolute path** stats each ancestor directory level by level; ancestors without metadata permission yield EPERM (symptom: sqlite reports `unable to open database file` while file owner and permissions are all normal). Services that only chdir and then write cwd via relative paths don't expose this pitfall, so it can lurk for a long time; `read: full` is not exempt either — the hidden root's carveout blocks the cwd ancestors that fall under `pm3.home` along with it
- `network: true` writes `(allow network-outbound (remote ip))`: a bare `(allow network-outbound)` also lets unix sockets through, which hands `pm3.sock` to the service. The Linux side doesn't rely on this — measured: under `--ro-bind / /` connect fails directly with EACCES (a read-only mount has no write permission), and after a `--tmpfs` shadow it's ENOENT
- **`network: true` needs two independent paths allowed to resolve domains / read system DNS** (missing either: curl/cloudflared report `Could not resolve host`, or mihomo falls back to the built-in `8.8.8.8` and can't resolve intranet domains → intranet services all break going DIRECT):
  - `(allow network-outbound (literal "/private/var/run/mDNSResponder"))` + mach-lookup `com.apple.mDNSResponder`/`mDNSResponderHelper` — getaddrinfo resolves via mDNSResponder (unix socket + mach port)
  - `(allow file-read* file-test-existence (literal "/private/var/run/resolv.conf"))` — the Go resolver reads resolv.conf for system DNS (intranet nameserver). These are **two separate paths** from mDNSResponder: when curl works via the former, mihomo (which reads the file) can still be stuck on the latter
  - Verification: inside `sandbox-exec -p "$(cat <assembled profile>)"`, `cat /var/run/resolv.conf` should show the intranet nameserver, `curl https://<intranet domain>` should return 302, and `nc -z -U ~/.pm3/pm3.sock` must still exit 1 (pm3.sock isolation must not be weakened)
- **Services using Metal/GPU (llama.cpp and the like)**: the base policy allows iokit `AGXDeviceUserClient`/`IOGPUDeviceUserClient`/`IOSurfaceRootUserClient` + mach-lookup `com.apple.MTLCompilerService` + sysctl `hw.cpusubfamily`; minimal read grants `/System/Library/Extensions` (GPU driver bundle), `/System/Library/CoreServices` and `path-ancestors "/System/Library"`. Missing iokit reports `ggml_metal_init: picking default device: (null)`; missing the compiler service reports `does not have a precompiled Metal library` then still `failed to create llama_context`. Measured: `com.apple.windowserver.active` is **not needed**; don't allow it for convenience
- **Services with recursive `fs.watch` (Node/frontend dev servers) MUST have mach-lookup `com.apple.FSEvents`**: libuv uses FSEvents on macOS; when denied it **silently falls back** to kqueue, opening an fd per directory, and scanning `node_modules` yields `EMFILE: too many open files, watch` and crashes the whole process. The symptom is highly misleading — it reports fd exhaustion; raising `ulimit -n` only postpones the blowup (measured: still blows at 65536), while the same code outside the sandbox is perfectly fine. **Denied only once** (initialization failure means fallback for the whole run), and in `log stream` it's easily drowned out by GPU/log noise
- When a service reports `Operation not permitted`, first check whether the external program it calls is a perl script: macOS has no `sha256sum`; `shasum` is a `/usr/bin/perl` script, and under minimal read `/System/Library/Perl/*/CORE/libperl.dylib` is unreadable → dyld fails outright, while the caller often treats it as "command output was empty" (symptom: `sha256 mismatch: expected <value>, got ` — empty at the end)
- To find out "what exactly the sandbox denied" use `log stream --style compact --predicate 'eventMessage CONTAINS "deny"'` (start it in the background, then run the program under test): SBPL's `(trace "<file>")` produces no file on modern macOS; don't waste time on it

#### bwrap (Linux)

- **MUST NOT add `--new-session`** (codex added it; pm3 must not): setsid takes the service out of bwrap's process group, `kill -TERM -<pgid>` can't reach it, and graceful stop degrades into "kill bwrap → pid namespace collapses → kernel SIGKILL". The TIOCSTI surface is covered by the kernel `dev.tty.legacy_tiocsti=0` (default since Linux 6.2) and "stdin is `Stdio::null()`"
- The cgroup namespace entry MUST be written as `--unshare-cgroup-try`, not `--unshare-cgroup`: cgroup namespace needs kernel 4.6+; the hard form makes bwrap exit outright on older kernels ⇒ the service can't start. `user`/`pid`/`ipc`/`uts` use the hard form (these four exist everywhere)
- Mount order is security semantics: `--tmpfs <hidden>` → `--bind <granted>` (shallowest first) → **then** `--tmpfs` the hiddens that fall under a granted (`nested_in`)
- MUST NOT add `--die-with-parent` (children must not die with a daemon handover; see "Children do not die with the parent" above)

### Processes

- `TokioProcessLauncher::wait` removes the `Child` from the map before awaiting, so "is it alive" must be tracked separately in a `live: HashSet<u32>` (insert at spawn, delete after wait returns)
- An adopted process is not a child (`adopt` only inserts into `live`, not `children`); it can only be polled via `ps`; and after a daemon handover **every** unchanged service takes this path → liveness probing MUST go through the shared `AdoptedWatch`: one poller task issues one `ps -ww -o pid=,lstart= -p <csv>` per tick covering all watched pids, and each waiter awaits its own oneshot. With one task per pid each forking `ps`, 20 services would be 20 child processes per second. `PsProcessProbe::identity` reuses `identities(&[pid])`; the token is still the `lstart` text (comparable across versions)
- The value sourcing of `kill_signaler` (process-group signals) and `ps_probe` (`ps -o lstart=` identity tokens) is a hard constraint; see root `CLAUDE.md` "Processes and signals" and "Identity fingerprint and takeover"
- **Three `ps` calls each have their own job; MUST NOT be merged**: `BATCH_FORMAT` (`pid=,lstart=`, identity tokens; `parse_report` splits at the first space and treats the entire remainder as the token), `resident_memory_kib` (`pid=,rss=`, memory circuit-breaker tick), `resource_usage` (`pid=,rss=,pcpu=`, the resource columns of `list`/`describe`, sampled on the request path, not in the tick). Adding a column to the first one makes memory fluctuations misjudged as pid reuse (consequences in root "Memory circuit breaker")
- `AdoptedWatch` cannot be reused for self-spawned children: `wait_for_exit` checks `is_child` first and children go through `Child::wait`, so that polling is empty in the normal case; its cadence backs off to `daemon_poll_max_interval_ms`

### Scheduling

- `random_expand.rs` MUST expand `~`/`a~b`/`a~b/n` into concrete numbers for croner **on every `arm_timer`**; expanding only once at load time loses the "re-draw on every fire" requirement
- croner's `find_next_occurrence` carries the input `start`'s **sub-second remainder verbatim into the result** (asking at `10:00:00.400` yields `10:55:00.400`) → the same cron period asked at different moments gives different `fire_at_ms`; once two `arm`s straddle a whole-second boundary, the `Fire` event is dropped because `fire_is_due` doesn't match (symptom: cron tests flake about 0.5% of the time, `next_fire_ms` has an extra `001` at the tail). `next_fire_ms` MUST first truncate the input to whole seconds (`after_ms - after_ms % MILLIS_PER_SECOND`)

### Service managers

- Unit file locations are derived per OS convention **in this layer** (`~/Library/LaunchAgents/{label}.plist` / `~/.config/systemd/user/{label}.service`) and **do not go into config** — a single config item cannot be correct for both platforms at once; `$HOME` is injected by `frameworks`, and tests pass a tempdir so real `~` is never touched. But **the manager binaries' paths do go into config** (`ServiceProgramSet::from_config`; see root `CLAUDE.md` "Configuration and paths"): `ServiceProgramSet` deliberately has no `Default` impl; the only production construction point is `open_service_session`; tests can still inject stand-ins via `ServiceContext.programs: Option<&_>`
- **systemd and launchd's "when to restart" semantics are unified by `restart_condition`**: `always` → systemd `Restart=always` / launchd `KeepAlive=<true/>`; `on-failure` → systemd `Restart=on-failure` / launchd `KeepAlive=<dict><key>SuccessfulExit</key><false/></dict>`. The default is `always` (consistent with the intent of `restart.autorestart: true`; older versions behaved inconsistently between the two managers — to keep the old semantics after upgrading, explicitly set `pm3.service.restart_condition: on-failure`). Windows (schtasks) is not part of this table: Task Scheduler only has RestartOnFailure; the unified semantics are implemented by the constant `exit /b 1` at the end of the `.cmd` wrapper script, and both `restart_condition` values behave identically on Windows (see root `CLAUDE.md` "Windows")
- systemd's escape table is down to a single `escape_value`; `quote_token` delegates to it and adds a pair of quotes → adding escape rules means changing only `escape_value`; MUST NOT be duplicated again — missing one copy produces "arguments re-parsed by systemd; the unit installs but won't start"
- `UnitCommand.env` is only filled by `user_scoped()` (one `XDG_RUNTIME_DIR`, value from `UnitProgramSet.runtime_dir`): without it `systemctl --user` can't reach the user bus in a non-login session, while launchctl and loginctl don't use the user bus, so their command env must be empty. New systemctl subcommands MUST go through `user_scoped`; don't assemble `--user` yourself
- `install_plan` takes `LingerState`: when `Enabled`, the `enable-linger` step is not generated (it goes through polkit and always fails in a non-interactive session). The check is in `runner::linger_state`; launchd returns `Unknown` directly (no forking loginctl); `dry_run` also queries once first, so the fake loginctl stand-in must dispatch on `$1` (`show-user` answers `yes`/`no`, `enable-linger` is counted separately)
- **Only `systemctl --user` depends on `XDG_RUNTIME_DIR`** (`loginctl` uses the system bus and is unaffected — don't conflate the two when troubleshooting): in a non-login session (agent/CI shell) it's empty → calls through systemctl fail, with text varying by systemd version (`Failed to connect to bus: No medium found`, or `... $DBUS_SESSION_BUS_ADDRESS and $XDG_RUNTIME_DIR not defined`). `frameworks`' `host_runtime_dir()` falls back to `/run/user/<uid>` when the variable is absent (uid taken from the owner of `/proc/self`; macOS has no `/proc` so it's `None`, and launchd doesn't need it); it is injected via `UnitProgramSet.runtime_dir` only into those `systemctl --user` commands ⇒ `just install` and `pm3 startup`/`pm3 unstartup` need no manual export; `systemctl_show_main_pid` (`pm3 install` querying MainPID) is likewise injected via `user_scoped`
- `loginctl enable-linger` **without a username is legal** (`enable-linger [USER...]`; omitted means the caller): without authorization it only reports polkit `requires interactive authentication` and does **not** report a missing argument → don't assume the command was written wrong and add a username. So it's a `TryRun` in the plan (failure only warns and appends `skipped: ...`); MUST NOT be changed back to `Run`: the unit and enable are already in effect, and reporting rv=1 overall makes operations think the install failed. Still seeing `skipped:` means linger really isn't on; have an account with sudo run it once, otherwise the user manager's reclamation after logout takes the daemon down with it
- Querying linger MUST pass the uid (`loginctl show-user <uid> -p Linger --value`): **without a username it prints an empty string with rv=0** (`show-user` with no argument means "the user of the current session"; a non-login session has no session) → judging by "non-zero exit means not found" misreads "linger already on" as off, running a doomed `enable-linger` for nothing. So `loginctl_show_linger` returns `None` when the uid is unknown, and the decision falls back to `Unknown`
- `capture()` MUST wrap a `command_timeout_ms` timeout: `systemctl --user` in a bus-less non-login session and `launchctl load` when launchd is busy can both hang for a long time; without a timeout `pm3 startup`/`pm3 unstartup` can block indefinitely. Failure goes through `ServiceCommandError::Stalled`
- A failed `ServiceStep::Run` aborts the whole plan; a failed `TryRun` only logs warn and collects the reason into the skipped list returned by `execute_plan` (both `install_service`/`uninstall_service` append it to the end of the report) → steps where "failing to install must be an error" use `Run`; steps where "failing is fine, only later usability is affected" use `TryRun`
- **All service-manager calls on the uninstall path are `TryRun`**: making `launchctl unload` / `systemctl --user disable --now` / `daemon-reload` a `Run` would let "job not loaded" or "a bus-less non-login session" block `Remove{unit_path}` behind them; the unit file could never be deleted, every rerun fails the same way, and the first step of the handover order in root `CLAUDE.md` is exactly `pm3 unstartup`. The success criterion of uninstall is "the unit file is gone", not "the manager agreed"
- When `execute_plan` fails it **rolls back the files created this run** (those where `try_exists` was false before `Write`): a failed `load` during install leaves no half-installed state for `query_status` to falsely report `installed, not running`; pre-existing files that were merely overwritten are not rolled back (they may be the operator's own)

### The single change point for persisting intent

- The two paths that write `cfg_dir/<name>.yaml` (apps file and `pm3 start --name`) MUST share **the same** `fold_entry`: it folds `script`/`cwd`/`args`/`sandbox.writable_roots` back into `${HOME}`/`${PM3_SERVICE_CWD}` and dedupes roots. A second copy inevitably diverges; the symptom is the same declaration encoding into two different yamls, and `pm3 start <apps-file>` being refused by `reconcile` (the diff is just one duplicated root line, or all `-"${HOME}/x"` / `+"/Users/me/x"`). New path-bearing fields change only `fold_entry`
- New `${...}` placeholders MUST be registered as reserved names in `substitute_env_vars` (the `SERVICE_CWD_NAME` branch), otherwise loading the cfg file fails outright with `EnvVarNotSet` for "variable unset with no default"; reserved names do not support `:-` defaults

### Service file read/write

- Reading a service/config file MUST distinguish "does not exist" from "read failed" (`read_existing` treats only `NotFound` as `None`; everything else returns `ServiceError::Read`): `read_to_string(..).unwrap_or_default()` / `.ok()` treats non-UTF-8 content, insufficient permissions, and "the path is now a directory" all as "file does not exist" ⇒ `reconcile` judges Stale and silently overwrites the operator's config even without `--force`; and after `ServiceUndo` records the prior state as `None`, rollback takes `Restore::Remove` — **deleting** the user's original file instead of restoring it
- An empty file is not the same as a nonexistent file: when the content is empty but differs from the new content it MUST go through `Conflict` (requires `--force`); don't keep using "`existing.is_empty()` means Stale"
- `forget` (deleting a service file) failure MUST log warn (except `NotFound`): swallowing it lets `pm3 delete` still report success, the on-disk file and daemon state diverge from then on, the next `start` gets refused by `reconcile` diffing against the old file, and the reason leaves no trace in any log

### Log read side

- `read_tail` stops scanning back at the `pm3.log_read_max_bytes` budget; the first line may be cut → when `start > 0` the buffer's first incomplete line is discarded; `LogFollower.pending` past the limit is released as one whole line. `LogFollower::resync` already handles both truncate and rename+recreate (the rationale for the limit is in root `CLAUDE.md` "Logs")

### Serialization

- `serde_yaml2` serializes an empty `BTreeMap`/`Vec` as `~`, and deserializing that back into a map fails → collection fields always get `#[serde(default, skip_serializing_if = ...)]`
- `serde_yaml2::to_string` output is not human-readable (quoted keys, odd indentation): yaml meant for humans to read and edit MUST be hand-rendered, backstopped by a round-trip test of "encode → parse back equals"

### DTO

- Adding a field to `ProcessView` pushes `DaemonReply::Described` past the clippy `large_enum_variant` threshold → put `#[expect(..., reason = "one reply travels per CLI command")]` on the enum; don't Box just to pass the lint (it would ripple through the whole controller/presenter chain)
