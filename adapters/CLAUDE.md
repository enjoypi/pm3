# adapters — bidirectional format conversion and Port implementations

Controller / Presenter / Gateway / DTO all live in this layer. No business-rule decisions, no use-case orchestration.

- **XDG defaults cannot be written in yaml**: `substitute_env_vars` does not expand nested defaults, so `${PM3_STATE_DIR:-${XDG_STATE_HOME}/pm3}` leaves the inner form as literal text. The repo's `config.yaml` keeps every root empty (`${PM3_STATE_DIR:-}`) and the derivation lives in `paths.rs`
- A `pm3.home` that is set (env or config) means **legacy single-root mode**: all four XDG variables are ignored and every path stays where it was. That is what keeps the e2e suite and `PM3_HOME=/srv/pm3` installs working unchanged
- **`ps -g` MUST NOT be used to select a process group**: on procps-ng (Linux) `-g` selects by *session*, and pm3's children run `process_group(0)` — setpgid, not setsid — so their sid never equals their pgid ⇒ `ps -g <pgid>` exits 1 with empty stdout, `read_ps` accepts that as `NO_SUCH_PROCESS_CODE`, and the group reads as drained while a grandchild still holds its resources. macOS's BSD `ps` happens to read `-g` as pgid, so the platforms diverge silently and only Linux breaks. Group membership MUST come from `-A -o pid=,pgid=` filtered on the pgid column
- **A fake `ps` in a test fixture pins nothing about real `ps` semantics**: the whole `-g` defect sat under a green suite because every probe test shipped its own `#!/bin/sh` stand-in. Any probe whose correctness depends on a real selector MUST also have a test that spawns a real process group and runs the host's `/bin/ps`
- **`sun_path` is 104 bytes *including* the NUL** ⇒ the longest bindable socket path is 103, which is why the constant is split into `SUN_PATH_CAPACITY` (104) and `LONGEST_SOCKET_PATH` (103) rather than leaving a `>` / `>=` judgement call at the comparison. Measured: macOS binds 103 and refuses 104, Linux binds 107 and refuses 108; pm3 takes the stricter value on both. Off-by-one here does not surface as a validation error but as an opaque `bind` failure much later
- **Every root MUST route through `expand_home`**: `resolve_runtime_root` once did `PathBuf::from(declared)` while `derivable_root` in `config/validate.rs` accepts a leading `~` ⇒ `runtime_dir: "~/run"` produced a *relative* socket path, which the launchd daemon and the operator's CLI resolve against different cwds — the same two-daemons-one-dump failure the `$TMPDIR` note warns about
- **`dominant_roots` compares normalized, not raw**: excluding self by `other == root` while judging coverage with `covers_path` (which normalizes trailing slashes) made `/srv/pm3/` and `/srv/pm3` cancel each other out, emptying `unreadable_roots` ⇒ a confined app could read pm3's own state root, and the `$TMPDIR` over-grant guard stopped firing. Identical roots MUST be settled by index so exactly one survives
- **The shared environment lives in the config root, per-app ones in `cfg_dir`** — deliberately, since the shared file is pm3's own configuration. When an operator sets `pm3.cfg_dir` and drops the shared file beside their service files it is simply ignored, so `warn_misplaced_global_env` MUST stay wired into daemon startup; that warning is the only thing standing between the operator and every app launching without those values
